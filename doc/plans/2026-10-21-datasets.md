# Plan: Databases (Notion-style structured data) and datasets

Status: plan, with the user's decisions recorded (section 8). No slice is merged yet.

## Context

Companies produce structured data all the time: research findings, leads, test results, price lists, triage logs, eval labels. Today that data lands in comments, markdown documents or attachments. Nothing gives it a schema, so an agent cannot filter it, a routine cannot append to it safely, and nobody can export it as a stable dataset.

This plan adds **databases**: company- or project-scoped tables with a typed schema of properties, rows, and (later) saved views, like Notion databases. Board users, agents and routine steps create and fill them. Rows link to tasks, agents, projects, routines, runs and artifacts. A database can be exported and frozen into immutable **snapshots** (dataset versions) for evals and analysis.

In plain words: a database is a spreadsheet that Paperclip understands. Every column has a type, every row knows who wrote it and in which run, and a snapshot is a frozen copy that another process can cite by version.

### Core or plugin

`ROADMAP.md:19` says Paperclip keeps a thin core, and plugins carry "knowledge bases ... doc editors, and other product-specific surfaces". A plugin could build databases on `ctx.db` (`plugin_database.ts:23-75`).

The plan uses **core** (decision 1), for four reasons:
1. Rows link to core work objects (tasks, runs, agents, work products) and must obey core authorization, including the low-trust boundary (`server/src/services/authorization.ts:985-1139`). A plugin cannot join that decision.
2. AGENTS.md rule 8 needs UI, OpenAPI and CLI parity. Plugin routes are not in the core OpenAPI document or the `paperclipai` CLI.
3. Agents in remote sandboxes reach the API only through the static bridge allowlist (`packages/adapter-utils/src/sandbox-callback-bridge.ts:170-300`), which is core.
4. `doc/GOAL.md:26` lists "company state stay[s] attached to the work" as a control-plane job.

The user chose core (decision 1).

## Goal

- A board user, an agent or a routine step can create a database, define typed properties, and create, read, update and delete rows, through the UI, REST, the CLI and agent runtime tools.
- A database is scoped to the company or to one project. Company boundaries always hold.
- Rows record who wrote them, in which run, and can link to tasks, agents, projects, routines, runs, work products, attachments, documents, goals and other rows.
- A database can be exported (CSV, JSONL) and frozen into immutable, numbered snapshots that work products and evals can cite.

## Non-goals

- A general SQL engine, formulas, rollups, or per-database Postgres tables.
- Realtime collaborative cell editing. Last write wins per property, with an optional revision check per row.
- Storing secrets or credentials.
- Analytics at warehouse scale (millions of rows). The row cap (below) keeps queries cheap. Large data belongs in a warehouse or a plugin.
- Prompt injection of database content into agent prompts. Agents read rows on demand. A `database://` mention is a possible follow-up (coordinate with `policy://`).
- Including databases in company portability (zip export/import) or the company archive in the first slices. The export-fidelity counter warns instead (slice 1a).
- A new routine step kind. Steps write through their agent.
- Writes by low-trust agents (see Permissions). They read only, inside their boundary.

## User stories

1. **Board user.** I create "Customer research" with Name, Status (select: new, contacted, won, lost), Score (number) and Source (URL). I edit cells inline, filter on Status = won, sort by Score, and export CSV for a meeting.
2. **Agent.** While working on a task, I create "Competitor pricing" in the task's project. I upsert 120 rows with `key` = the competitor's domain, so a retry does not duplicate them. Each row links to my task. At the end I take a snapshot and register it as a work product on the task.
3. **Routine step.** A weekly routine has steps `collect` then `score`. The `collect` agent upserts leads into "Leads" with `key` = the lead's external id and writes only the lead properties. The `score` agent queries rows where Score is empty and sets Score. Upserts merge per property, so next week's `collect` run does not erase the scores. A re-run of the week is idempotent.
4. **Project.** The "Mobile app" project has a project-scoped "Bug triage log". It shows on the project page. Standard agents working on the project write to it. A low-trust reviewer agent contained to that project can read it, but cannot write to it and cannot see company-scoped databases.
5. **Dataset consumer.** An eval owner freezes "Labeled support tickets" as version 3. The eval cites version 3, so a later edit to the live database does not change the eval's inputs.

## 1. Data model

### Storage choice

| Option | How | For | Against |
|---|---|---|---|
| **A. Rows as JSONB with a validated typed schema** (chosen) | One `database_rows` table. A `cells jsonb` column holds `{propertyKey: value}`. The schema lives on the database row and is validated in `packages/shared` on every write. | No DDL at runtime. Migrations stay static and reviewable (`doc/DATABASE.md:215-235`). One table to scope, index, back up and delete with the company. Matches existing jsonb patterns (`routines.steps`, `cases.fields`). GIN works on dev and prod Postgres. | Filters on a property use jsonb expressions without a per-property index. Type safety is in application code, not in Postgres. |
| B. EAV (one row per cell) | `database_cells(row_id, property_key, text_value, number_value, ...)` | Typed columns per value kind. Property indexes are possible. | A page of 50 rows with 20 properties reads 1,000 cells. Every filter is a join. Writes touch many rows. Bulk import is slow. |
| C. A Postgres table per database | DDL on create and on every schema change. | Native types, constraints and indexes. | Runtime DDL across a multi-tenant instance. It bypasses the drizzle migration journal, the migration safety checks (`packages/db/src/check-migration-safety.ts:14-18`) and company deletion (`server/src/services/companies.ts:629-707`). Table count grows without bound. Plugins already have this path (`plugin_database.ts`), with its own review. |

Choice: **A**. A row cap per database keeps a scan inside one database cheap. The `(database_id, ...)` indexes cut every query down to one database first. The column is named `cells`, not `values`, because `VALUES` is an SQL keyword and raw `sql` fragments would need quoting.

### Property types

A property definition is validated by a discriminated zod union in `packages/shared/src/databases.ts`, in the style of `packages/shared/src/routine-steps.ts`:

```ts
{ key: "score", name: "Score", type: "number", position: 2, archivedAt: null, config: { ... } }
```

- `key` is the property's identity: a slug `^[a-z][a-z0-9_]{0,63}$`, unique in the database including archived properties, and **immutable**. `name` (≤ 100 characters) is free to rename. Agents write cells by key. CSV and JSONL use the key, so exports are stable across renames.
- Each database has exactly one property of type `title` with key `title`. It is created with the database, cannot be archived, and is stored in `database_rows.title`.

### Concurrency

- Every row insert, delete, revival and bulk upsert locks the database row first (`UPDATE databases ... RETURNING` inside the write transaction). The same lock checks the row cap, allocates `seq` from `next_row_seq`, updates `row_count`, and returns the `properties` that the write is validated against. Writers to one database are serialized; writers to different databases are not. This replaces an advisory lock and keeps the counter exact.
- A cell edit (row PATCH) does not change membership. It reads the database row with `FOR SHARE` (so a concurrent schema change waits), validates against that schema, then updates the row. It never updates the `databases` row, not even `updated_at`. Every write path takes the database row before the row, so lock order is the same everywhere and writers cannot deadlock. A PATCH uses the row's `revision` when the caller sends `expectedRevision`.
- Schema writes compare `schema_revision` in the `UPDATE ... WHERE schema_revision = $expected` statement, so two concurrent schema edits cannot both win.

### Schema changes with existing rows

The schema endpoint takes the full property list plus `expectedSchemaRevision`. The server diffs it against the stored list:

- **Omitting** an existing property is a 422. The PUT never deletes. Archiving is explicit.
- **Add** a property: no row is rewritten. A missing cell reads as null.
- **Rename**, **reorder**, **edit config** (for example a number format): metadata only.
- **Add or rename a select option**: metadata only, because rows store option ids.
- **Remove a select option**: metadata only. Reads drop unknown option ids. Writes refuse them. No mass update runs.
- **Archive a property**: it gets `archivedAt`. Its cells stay in rows, hidden from reads and exports. Restoring it brings them back. Its key stays reserved.
- **Purge an archived property** (slice 5): a chunked keyset update on `seq` removes the key from `cells`, using the batching rules of `doc/DATABASE.md:215-226`. Then the key is free again.
- **Change a type**: refused (422) in slices 1 to 4. The user adds a new property and copies values with a bulk update (by row `id`, see Performance). Slice 5 may add safe conversions (text and url, select to multi-select, number to text) as a chunked rewrite.
- Every schema change logs `database.schema_updated` with the added, changed and archived keys.

### Soft delete and history

- A database is archived, never deleted, by the API in these slices. Archived databases are read-only and hidden from default lists. A board user or a database manager can restore one. A hard delete happens only through company removal.
- A row is soft-deleted (`deleted_at`). Deleted rows do not count toward the cap and do not show in queries. An upsert whose key matches a deleted row revives it with only the cells the request sends, and reports it as `restored` (Performance). Slice 1a ships delete. Slice 5 adds an explicit restore route, which brings back the old cells, and a trash view.
- **History.** Every mutation writes an activity entry (Surfaces). Slice 5 adds `database_row_revisions`: an append-only copy of `title` and `cells` per change, with actor and run, in the pattern of `document_revisions.ts:7-34`. Retention keeps the last 50 revisions per row (decision 10).

### Dev and test database compatibility ("PGlite")

The brief asks for PGlite compatibility. Paperclip no longer runs PGlite. `mode: "pglite"` is a legacy alias that becomes `embedded-postgres` (`packages/db/src/runtime-config.ts:113-130`). Dev and tests run embedded PostgreSQL 18 (`packages/db/package.json:53`, `packages/db/src/test-embedded-postgres.ts`), and Docker runs `postgres:17-alpine` (`doc/DATABASE.md:56`). (`AGENTS.md` §4 and `doc/SPEC.md:435` still say PGlite; that text is stale and out of scope here.)

The design uses only features that work on both versions and are already in the repo: jsonb, GIN (`jsonb_path_ops` is core Postgres, no extension), partial unique indexes (`company_secrets.ts:45-53`), row locks, advisory transaction locks, and `pg_trgm` (already installed by `0051_young_korg.sql:1`) for later title search. It uses no new extension, no generated column and no runtime DDL. Service and route tests run on embedded Postgres, like the rest of the server suite.

## 2. Permissions

### Company boundaries

- Every query filters on `company_id`.
- `/databases/:id` routes load the database through `getAccessibleResource` (`server/src/routes/authz.ts:182-195`). A database of another company answers the same 404 as a missing one.
- Every row, snapshot and view lookup filters on `(id, database_id, company_id)` together, never on the child id alone. So `/databases/A/rows/<row of B>` is a 404 and cannot borrow A's authorization to act on B. A test pins this.
- `project_id`, link targets, snapshot assets and views must belong to the database's company.

### Authorization actions

The server adds three actions to `AuthorizationAction` (`server/src/services/authorization.ts:70-88`) and one resource type to `AuthorizationResource` (`:90-105`):

```ts
| "database:read" | "database:write" | "database:manage"
| { type: "database"; companyId: string; databaseId?: string | null; projectId?: string | null;
    createdByAgentId?: string | null; agentAccess?: "write" | "read" }
```

`database:write` covers row writes. `database:manage` covers create, metadata, schema, archive, restore and snapshot creation. Routes call `accessService(db).decide` (`server/src/services/access.ts:406-412`), as `assertPipelineWriteAccess` does (`server/src/routes/pipelines.ts:353-375`).

`decide` checks the agent, then checks the agent's responsible user by running the **board** branch for that user (`authorization.ts:2405-2440`). A new action with no board mapping returns `deny_unsupported_action` (`authorization.ts:1876-1880`), and only issue actions are exempt from that (`:2425-2431`). Standard agents also default-deny unmapped actions (`:2350-2357`). Slice 1a therefore adds an explicit branch for each actor kind:

| Branch | `database:read` | `database:write` | `database:manage` |
|---|---|---|---|
| Board user (`decideBase`, next to the visibility actions at `authorization.ts:1833-1875`) | any active member, viewers included | non-viewer members | non-viewer members |
| Cloud tenant (`authorization.ts:1716-1752`) | same as board | same as board | same as board |
| Standard agent, same company | allow (default visibility, as `project:read`, `authorization.ts:2153-2168`) | allow when `agentAccess = write` | create: allow. Existing database: the creator agent while `agentAccess = write`, or a `databases:manage` grant (slice 6) |
| Low-trust agent (`decideLowTrustAccess`, `authorization.ts:985-1139`) | only a project-scoped database whose project passes `projectWithinLowTrustBoundary` (`authorization.ts:965-974`) | deny | deny |
| `task_bridge` and `skill_test` keys | deny (the default at `authorization.ts:1266`) | deny | deny |

Only board users change `agentAccess`.

Trust resolution loads the project of the resource to apply its policy, but only for issue and project resources (`loadResourceContext`, `authorization.ts:882-892`). Slice 1a adds the `database` case, so a project-scoped database's project policy applies like an issue's.

**The responsible-user intersection** then applies to every agent decision. An agent acting for a viewer can read but not write. Route tests cover: board member, viewer, standard agent, agent whose responsible user is a viewer, low-trust agent inside and outside its project, `task_bridge` key, cross-company access, `agentAccess = read`, and a row id from another database.

`assertCompanyAccess` also blocks non-GET requests for viewers and for agents acting for viewers (`server/src/routes/authz.ts:93-101`). This is why every read in this plan is a GET, including filtered queries.

### Why low-trust agents only read

`doc/LOW-TRUST-PRESETS.md:35-38` says containment "prevents raw untrusted output from being automatically promoted into higher-trust agent context". Other low-trust outputs carry `sourceTrust` (`documents.ts:23`) and are redacted for higher-trust readers (`server/src/services/source-trust.ts:12-45`). Rows have no such marker. A low-trust write into a database that standard agents read would bypass that rule.

So low-trust agents read only, inside their boundary. The list route filters by the same boundary. `decideLowTrustAccess` returns null for actions it does not know, which falls through to the standard rules (`authorization.ts:1137-1138`), so the branch is mandatory, not optional. A low-trust deny returns at once. A low-trust allow returns at once only for the actions listed at `authorization.ts:1975-1988`, so `database:read` joins that list. If low-trust writes are needed later, a slice adds `source_trust` on rows and applies the quarantine redaction to reads, exports and snapshots (decision 11).

### Run and work-mode checks for agent writes

- **A valid run.** An agent write needs a run that belongs to the same agent and company. For an `agent_jwt` actor, the run comes from the verified token. For an agent API key, the `x-paperclip-run-id` header is not trusted as such (`server/src/middleware/auth.ts:255-267`). The server looks the run up with the agent and company, as `resolveLegacyRunResponsibleUserId` does (`server/src/middleware/auth.ts:92-108`), and answers 422 when it does not match. Only a validated run id goes into `created_by_run_id`, so a forged id can neither break the FK nor forge provenance. (`server/src/routes/pipelines.ts:265-275` checks presence only, so it is not the model.)
- **Ask and Plan modes.** There is no global REST work-mode gate. Only routes that call `projectToolContext(db, actor, true)` block writes in Ask and Plan (`server/src/routes/projects.ts:255-256`, `server/src/services/project-tool-context.ts:24`). That helper also refuses a run without a task (`project-tool-context.ts:17-18`), so the database write handlers do not call it as is. They apply the same work-mode rule only when the run is bound to a task, and recheck it inside the write transaction, as the projects route does. An Ask or Plan run gets 403 on writes and can still read. A run without a task (for example a timer run) has no work mode and can write.

### Grants (slice 6)

A new permission key `databases:manage` joins `PERMISSION_KEYS` (`packages/shared/src/constants.ts:1052-1074`). It is stored in `principal_permission_grants` with an optional scope `{ databaseIds?: string[], projectIds?: string[] }`, the same table and scope style as `tasks:assign_scope` (`doc/SPEC-implementation.md` §9.8). A granted agent can write rows in `read`-locked databases and manage any database in scope. Before slice 6, only the board and the creator agent manage a database. New keys flow into the access and portability validators automatically (`packages/shared/src/validators/access.ts:99`, `validators/company-portability.ts:89`). A standard agent needs an explicit grant for any `PermissionKey` (`authorization.ts:2306-2357`), so the key is never used for default access.

`agentAccess` and scoped grants are write controls on one object. `doc/SPEC-implementation.md` §9.5-9.6 defers per-object **visibility** controls to Pro and Enterprise. Databases keep company-wide visibility for in-company actors (except low-trust containment), and the SPEC addendum says so.

### Project scope

- `project_id` makes a database project-scoped. A board user or a database manager (the creator agent, or a grant holder) can move it between scopes with PATCH. A low-trust agent cannot.
- In V1 every in-company work object is visible to every in-company agent (`doc/SPEC-implementation.md` §9.5). Project scope therefore groups and contains; it hides data only from low-trust agents outside the project.
- When a project is deleted, its databases become company-scoped (`set null`). Projects are normally archived, so this is rare. An archived project's databases stay readable.

### Routine-step writes

A routine step is a task assigned to an agent (`server/src/services/routine-steps.ts:298-318`). The agent writes rows with its run token, so the normal agent rules apply. Provenance follows: row → `created_by_run_id` → the run's task → its `origin_kind = routine_step` and `origin_id` = the routine. No routine field changes in these slices. The skill shows the idempotent pattern: upsert with a `key` derived from stable input (for example the lead id), never from the run id, and write only the properties the step owns, so the per-property merge keeps other steps' cells.

### Untrusted content

- Rows written by agents are untrusted input for the agents that read them later. The skill tells agents to treat cell values as data, never as instructions. Each row keeps its writer and run, so the board can trace a bad row.
- Filter values are bound parameters, never SQL text (Performance).
- URL values allow only `http:` and `https:`. The UI renders them as external links with `rel="noopener noreferrer"`.
- CSV export escapes formula-injection characters in **text-typed** cells (title, text, url, select names). Number cells are written as numbers, because the existing pattern `/^[=+\-@\t\r]/` (`server/src/routes/activity.ts:17`) would turn `-5` into `'-5`.
- Text is rendered as plain text, never as HTML. Markdown rendering of text cells is out of scope.

## 4. Dataset export and versioning

### Export (slice 4)

- `GET /api/databases/:id/export?format=jsonl|csv`, streamed with the company-archive pattern: an async generator, abort on client close, `Cache-Control: no-transform` so compression does not buffer, and `drain` backpressure (`server/src/routes/company-archive.ts:24-110`).
- **JSONL**: the first line is a header `{kind: "database.header", databaseId, key, schemaRevision, properties, exportedAt}`. Then one line per row in `seq` order: `{kind: "row", id, seq, key, title, cells, createdAt, updatedAt, createdBy, updatedBy}`. `cells` uses property keys and output shapes (option names included). Relations export as `[{kind, id}]`. Archived properties are left out.
- **CSV**: columns `id, seq, key, title`, then active properties in order; the header row uses property keys. Multi-value cells are joined with `; `. Text-typed cells are escaped against formulas.
- Read permission applies. The company archive export is board-only (`server/src/routes/company-archive.ts:22-25`) because it carries run transcripts and costs that agents cannot otherwise read. A database export carries only rows the caller can already read through the rows route, so it gives no new access. Each export logs `database.exported`.

### Snapshots (slice 4)

A snapshot is an immutable, numbered copy of a database at one moment. It is the "dataset version" that other things cite.

| Column | Notes |
|---|---|
| `id` uuid pk, `company_id`, `database_id` | |
| `version` integer | 1, 2, 3 per database. Unique `(database_id, version)`. Allocated while the database row is locked. |
| `label` text null | For example "before relabel". |
| `schema` jsonb | The property list at snapshot time. |
| `row_count`, `byte_size`, `sha256` | Of the JSONL content. |
| `asset_id` uuid FK assets | The JSONL content, written through the storage service (`server/src/storage/service.ts:61-70`, namespace `database-snapshots`). |
| `created_by_*`, `created_at` | |

- Creating a snapshot needs `database:manage`: board users, the creator agent, or a grant holder. With the caps in Limits, an agent cannot fill storage.
- How it is built:
  1. Read the rows in one `REPEATABLE READ` read-only transaction and spool the JSONL to a temporary file, computing `byte_size` and `sha256` on the way.
  2. Commit the read transaction.
  3. Upload the file with `putFile`, which needs the size and hash up front for streams (`server/src/storage/types.ts:56-60`).
  4. Insert the snapshot row in a short transaction that allocates the version and rechecks the caps.

  An upload failure leaves no row. If the row insert fails, the server deletes the uploaded object best-effort (`deleteObject`). A crash between the upload and the insert can leave an orphan object, which is accepted: storage has no prefix listing, and company removal deletes no stored objects. Only one snapshot build runs per company at a time, because each build can spool up to 256 MiB to temporary disk. The build spans the upload, which runs outside any transaction, so a transaction-level lock does not fit. The build holds a session-level `pg_try_advisory_lock` on one dedicated connection for the whole build, and unlocks on that same connection in `finally`. A second build gets 409 `snapshot_in_progress`.
- Content is served from `GET /api/database-snapshots/:id/content`. Each download logs `database.snapshot_downloaded`.
- Content lives in instance storage, not in Postgres, so a snapshot does not double the database. Company storage destinations (`doc/company-storage.md:3-6`) can hold it later (decision 7).
- Snapshots are never edited. Deleting one is out of scope; it goes with company removal.

### Links between artifacts, rows and snapshots

- **Row → artifact**: a `file` or `relation` property links a row to a work product or an attachment (slice 3).
- **Artifact → row or snapshot**: a work product on a task can point at a row or a snapshot with two new `metadata.resourceRef` kinds, next to `workspace_file` (`packages/shared/src/validators/work-product.ts:73-77`):
  - `{ kind: "database_row", databaseId, rowId }`
  - `{ kind: "database_snapshot", databaseId, snapshotId, version }`

## 5. Performance

- **Bulk upsert** (slice 2): one transaction per request (≤ 500 rows, ≤ 8 MiB). Validation runs in memory first. Each item names a `key` or an `id`:
  - With `key`: one multi-row `INSERT ... ON CONFLICT (database_id, key) WHERE key IS NOT NULL DO UPDATE SET ... RETURNING ...` in drizzle `onConflictDoUpdate` with `targetWhere` and `setWhere`. The `SET` list and `setWhere` are the ones in the Merge and Revival bullets below. The `SET` list also sets `deleted_at`, `deleted_by_agent_id` and `deleted_by_user_id` to null, sets `updated_by_*` to the caller, and increments `revision`. `insertRowsInChunks` (`server/src/services/batch-insert.ts:35-70`) is a plain insert with no conflict handling and no `RETURNING`, so it is not used here.
  - With `id`: an update of an existing row of the same database, merged the same way. This gives rows without a key (for example rows made in the UI) a bulk-edit path.
  - **Merge, not replace**: `||` keeps the properties the request does not name. A request sets a property to null to clear it. Live rows whose cells do not change keep their revision and count as `unchanged`.
  - **Revival**: a key that matches a soft-deleted row revives it. A revived row gets **only** the cells and title the request sends: `cells = CASE WHEN database_rows.deleted_at IS NOT NULL THEN excluded.cells ELSE database_rows.cells || excluded.cells END`, and the title follows the same rule. So deleted data never comes back by accident. `setWhere` is `database_rows.deleted_at IS NOT NULL OR <something changed>`, so a revival always writes, even when the cells are equal, and `row_count` stays exact. A revived row counts as `restored` and is added back to `row_count`, subject to the cap.
  - **Edge cases**:
    - An `id` item that names a deleted row is a 404 for that item. Ids never revive; the restore route does (slice 5).
    - `POST /rows` with the key of a deleted row is a 409 (`row_key_deleted`), with a hint to upsert or restore. The single-row create never revives.
    - Two items with the same key or the same id in one request are a 422 during validation, before any SQL. Postgres would otherwise raise "ON CONFLICT DO UPDATE command cannot affect row a second time" as a 500.
  - Before the insert, the database row lock allocates `seq` values for new rows and checks the cap with the number of rows that will be created or revived. It returns the current `properties`, and the request is validated against that copy, so a concurrent schema change cannot slip past. Then the transaction updates `row_count` once and writes one activity entry and one live event.
- **Pagination**: keyset on `seq`, never OFFSET. The cursor is the last `seq` as a string. A sort on a property (slice 2) adds the typed sort value to the cursor, with `seq` as the tiebreak and nulls last. Timestamps are not used as cursors, because JavaScript dates keep milliseconds while `timestamptz` keeps microseconds (the workaround at `server/src/services/chat-channels.ts:28616`), and all rows of one upsert share `now()`.
- **Filters** compile to parameterized SQL. Property keys are checked against the schema first. Values are bound parameters, never string concatenation. Equality on select, multi-select and checkbox uses `cells @> $1`, served by the `jsonb_path_ops` GIN index. Text contains uses `ILIKE` with escaped wildcards. Number and date ranges use typed casts inside `CASE WHEN jsonb_typeof(...) = 'number' THEN ... END`, because Postgres does not promise the order in which `AND` evaluates its parts. Range and text filters scan one database's rows through the `database_id` indexes, which the 50,000 row cap keeps bounded.
- **Query limits**: the rows route sets `statement_timeout` to 5 s inside its transaction (`set_config('statement_timeout', '5000', true)`, the pattern at `server/src/services/execution-control-reconciliation.ts:77`). A timeout answers 422 with a hint to add a filter on an indexed property. At most 20 conditions and 3 sort keys. A page stops at 200 rows or 4 MiB.
- **N+1 risks and fixes**:
  - The database list reads `row_count`, never `count(*)` per database.
  - Relation and file cells for a page resolve with one query per target kind (at most about 11) plus one batched read check per kind, never one per cell.
  - Writer names for a page resolve in one agents query.
  - Backlinks use the `(company_id, target_kind, target_id)` index.
  - The UI loads one page of rows plus the schema, never one request per row.
- **Expected cost**: a 50,000-row database with 20 properties at 2 KiB per row is about 100 MB of jsonb. A filtered scan of it should take well under a few seconds on modest hardware; indexed equality filters and the default order should take milliseconds. These are estimates. Slice 2 measures them with a seeded 50,000-row test (decision 5).

## 8. Decisions

The user answered the open questions on 2026-10-21. These answers are now part of the plan.

1. **Core or plugin.** Core. Rows link to core work and must follow core permissions, parity and the bridge, although `ROADMAP.md:19` prefers plugins for product-specific surfaces.
2. **Name.** "Databases" in the UI, API and CLI. A frozen, numbered snapshot is a dataset version.
3. **Default agent access.** Every standard agent in the company can write rows in a new database by default (`agentAccess = write`, like tasks). The board can lock a database with `agentAccess = read`.
4. **Agent-created scope.** Standard agents can create company-scoped and project-scoped databases.
5. **Caps.** 50,000 rows per database and 64 KiB of cells per row. Slice 2 measures them with the seeded test; a measured problem goes back to the user before the caps change.
6. **Flag in production.** `enableDatabases` stays off in production until slice 1b ships. Slice 1a is checked on a local instance with production-like data, or with the flag on for the check window only and off right after, with both times recorded. From slice 1b on, the flag stays on.
7. **Snapshot storage.** Instance storage. Company storage destinations can come later.
8. **Agent context.** Agents read databases on demand through the API, the CLI and the project tools. `database://` mentions can come later, with the same resolver as `policy://`.
9. **Portability.** Company export and import carry databases and their rows from slice 6.
10. **History retention.** The last 50 revisions per row (slice 5).
11. **Low-trust writes.** Low-trust agents only read. A later slice can add a source-trust marker and quarantine redaction on rows if a workflow needs low-trust writes.
