This plan **extends [`doc/plans/2026-09-10-agent-chat.md`](2026-09-10-agent-chat.md)**. It does not create a parallel chat backbone. Agent Chat already owns the persistent issue-backed transcript, conversation lifecycle, clarify-then-create-task policy, project handoff, shared composer, and task/artifact cards. Workroom adds an intent-first entry point, task context attachment, and selected-task actions on top of those contracts. The Workroom entry opens the existing `chats/:agentRef` conversation for the coordinator. The existing agent rail remains secondary navigation; choosing an agent is never required.

## Product contract

The user starts with one action: **Ask the workroom**. The sidebar label is **Workroom**. The user does not choose an agent or project before speaking. The built-in coordinator infers the responsible project and agent from the request and shows both as editable context before it delegates. The user can correct the inference without leaving the conversation.

The Workroom is a 1:1 surface. Conference Room Chat remains the separate team conversation behind `enableConferenceRoomChat`; its board route and sidebar row are not merged into Workroom. The Workroom must not add a rooms model, a second transcript, or a second skills channel. Add one product Workroom row in both supported sidebar shells: relabel the existing Chat row in the streamlined shell, and add the same single row to the production shell. Never render both Chat and Workroom rows for the same surface.

The right rail reuses Agent Chat's task and artifact cards. A checkbox or toggle on each card selects it while the card body keeps its existing link. Selecting several cards creates a single immutable selection snapshot for the next turn. The rail shows tasks the coordinator participated in, up to the existing limit. The actions live in the composer so the user can continue speaking in the same session:

- **Discuss**: ask the coordinator to compare or explain the selected tasks.
- **Validate**: ask it to inspect the selected tasks and return evidence or a decision request.
- **Request changes**: ask it to produce a change request that follows the existing review and approval path.

The rail is not a second batch toolbar. A selection can be removed from the composer without changing the task. Every action shows which task references were sent, the inferred project and assignee, and the resulting delegation or review receipt.

A compact composition sketch:

```text
+----------------------+-----------------------------------------------+----------------------+
| Sidebar              | Workroom                                      | Task / artifact rail |
|                      |                                               |                      |
|  Dashboard           |  Workroom: Ask anything                       |  [ ] Task A          |
|  Inbox               |  ------------------------------------------------|  [x] Task B          |
|  Workroom  <-------- |  User: Validate the selected rollout tasks    |  [ ] Task C          |
|  Decisions           |                                               |                      |
|  Tasks               |  Coordinator: I found 2 tasks in Project X.    |  Artifacts           |
|  Projects            |  Evidence: ...                                 |  Plan                |
|                      |  [Project X] [Agent inferred] [Task B]         |                      |
|                      |                                               |                      |
|                      |  [Discuss] [Validate] [Request changes]        |                      |
|                      |  [ context chips ]  Type a request...   Send  |                      |
+----------------------+-----------------------------------------------+----------------------+
```

The selection is ordinary conversation context. It does not create a new review state. Validation and change requests use `in_review`, Decisions, approvals, and their existing audit effects. Dismissal follows the semantics in #109 after that open PR merges; until then, dismissal acceptance tests must retain the current behavior as a compatibility check.

## Coordinator skill and system policy

The coordinator is a Paperclip-managed built-in agent. It receives a platform skill in the skills catalog and a default instruction bundle. Add the `enableWorkroom` catalog, validator, server-settings, and Experimental-UI contract, then make coordinator provisioning and the conversation route require both `enableBuiltInAgents` and `enableWorkroom`; existing `featureKeys` alone do not provide that mapping. The skill defines the Workroom loop:

1. Read the authorized company context needed to understand the request.
2. Reuse an existing project, task, skill, and agent when they fit.
3. Ask one focused clarification when project, ownership, scope, or approval authority is materially ambiguous.
4. Create ordinary assigned tasks with a plan, acceptance criteria, project, and assignee only after the request is clear.
5. Return a durable delegation receipt to the conversation.
6. Keep execution in the delegated task. The coordinator never performs the deliverable in the conversation task.
7. Use existing decisions, approvals, and `in_review` for validation and change requests.

The system prompt must state that the coordinator is read-mostly, has no execution workspace, and may delegate only through server-governed task/project operations. The server and tool gateway must enforce the same rule; prompt text is not a security boundary. A denied direct-execution attempt must be an auditable policy denial and must not create a workspace as a side effect.

The current built-in-agent model already supplies definitions, default instructions, bundled skill assets, restricted permissions, provisioning, and setup controls. The current permission shape does not yet prove an explicit “no execution workspace / delegate-only” capability: it exposes create-agent/create-skill controls and derives task assignment from role, grants, or active membership, while issue creation accepts execution-workspace fields. Therefore the implementation must first add a validation slice that traces every coordinator tool and write path. Propose a new principal kind only if that slice proves the built-in agent, permission, and tool policy cannot fail closed. A new principal would otherwise add a security gate and duplicate identity, membership, and audit paths.

Read-mostly means:

- read company-scoped projects, tasks, agents, skills, artifacts, activity, run summaries, and relevant decision state;
- create or update delegation records through normal task/project APIs;
- request a decision or review through existing governed paths;
- never edit source deliverables, execute code, create an execution workspace, approve its own request, or cross a company boundary.

## Evidence, Jev, and observability

Workroom emits an evidence bundle from real requests, decisions, and delegations. It does not score itself. Jev classifies and evaluates the bundle through the company evals contract in #92 and the shared client in #40.

The minimum evidence bundle should be versioned and include:

- request, conversation, run, and idempotency identifiers;
- normalized user intent and disposition (clarify, delegate, discuss, validate, or request changes);
- selected task references and the resolved project/agent context;
- delegation receipts, task plans, review/approval IDs, and policy-denial codes;
- direct-execution and cross-company boundary checks;
- timestamps, queue wait, duration, provider/model, usage, cost, and retry data when available;
- activity/run-log links and trace correlation identifiers;
- final state and evidence completeness, including missing or unknown values.

Jev should classify delegation correctness, intent/disposition, direct-execution violations, project/agent selection, task/context correctness, review/change-request correctness, idempotency, company isolation, trace completeness, latency, cost, and efficiency. Keep Product E2E and Runner Eval results as separate families. Do not introduce a Workroom scorer, a second metrics store, or first-party Telemetry events for company KPIs; use the run log and instance records for those measurements.

## Consequential choices

### Built-in agent or new principal

**Recommendation: use a built-in agent.** Existing definitions and provisioning already support a platform-owned role with a bundled skill, default instructions, restricted permissions, and a feature gate. The implementation must prove server/tool enforcement for no workspace and delegate-only behavior before shipping. If the proof fails because the current principal/permission model cannot express the boundary, document the failing paths and then introduce the smallest new principal capability with company scoping, audit attribution, and migration coverage.

### Per-user or per-company session

**Recommendation: one persistent Workroom session per user and company.** Reuse Agent Chat's existing company, user, and conversation identity model. Each person sees the company-scoped work they are authorized to see, and ordinary task visibility rules remain in force. Do not create one shared transcript for all users. A per-user session preserves context, avoids accidental disclosure, and still allows delegated tasks and decision receipts to be visible through normal company surfaces.

### Load-test scale

**Recommendation: stage deterministic tests before paid provider campaigns.** Start with a smoke run of 10 sessions and 100 requests, a medium run of 50 concurrent sessions and 1,000 requests, a large burst of 200 sessions and 5,000 requests, and a bounded 30-minute soak at 25 concurrent sessions. These are starting targets, not a promise about an undersized environment. The Jev and company-evals owners must agree the final scale, rate limits, evidence retention, and cost ceiling before a paid run. Classify queueing, provider, product, and grading failures separately. Keep live campaigns narrow and paid. Never combine Product E2E and Runner Eval scores.

## Non-overlap and handoff rules

- Agent Chat owns the conversation backbone. Workroom owns the intent-first composition and context actions.
- Conference Room Chat owns team chat. Workroom stays 1:1.
- The separate in-flight software-factory proposal owns the default coordinator bundle and any later sidebar addition. Workroom owns the conversation surface and lands its sidebar row first; any later sidebar addition rebases around it.
- Decisions, approvals, and `in_review` own review state. Workroom adds no new state.
- Jev and the company evals effort own classification, scoring, and campaign evidence. Workroom emits the evidence bundle and does not create a scorer.
- The launcher owns the single entry action. Search and New Task are replaced by the launcher according to #95; Workroom adds the single `Ask the workroom` launcher action and its one sidebar row, not another top-level entry point.
- Run log, activity, and existing instance records own observability and KPI data. Workroom does not create a second metrics or evidence store.

## Risks and mitigations

- A single coordinator can hit the current 50-open-decision cap per origin agent during batch Validate or Request changes (`PAPERCLIP_DECISIONS_OPEN_CAP`). The implementation must rate-limit, surface partial results, and define an owner-approved batching policy before increasing any cap.
- Jev submission can expose request content or create unapproved cost. Workroom never auto-submits; a person or agent must deliberately call the #92 eval run under D12. Redaction follows #92 D15/Q5, and any automatic submission needs a separate opt-in contract outside #92.
- The coordinator permission gap can permit direct execution through an unreviewed tool or HTTP fallback. Test every path and fail closed before rollout.
- The task rail is limited to the coordinator's participated tasks. The UI must state that scope and provide ordinary task navigation for anything else.
