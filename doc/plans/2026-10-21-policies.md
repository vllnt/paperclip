# Policies: written rules and guardrails for a company and its projects

Status: slice 1 implemented (2026-10-21). Slices 2 and 3 are planned below, with
code anchors and acceptance checks, so another team can build them.

## Goal

The board writes rules and guardrails once, at company level or for one project.
Agents read them. Agent instructions, skills and routines can point at them, and
agents that work on a project's tasks know which ones apply.

A policy is guidance in markdown. It does not enforce anything by itself. The
server keeps enforcing the guardrails it enforces today (see "Guidance and
enforcement" below). This plan builds no new rules engine.

## Naming

The product name is **Policies**, because the request uses that word. The code
uses it as follows:

| Layer | Name |
|---|---|
| Table | `company_policies` |
| Shared type | `CompanyPolicy` |
| REST | `/api/companies/:companyId/policies[/:key]` |
| Mention | `policy://<key>` |
| CLI | `paperclipai policy …` |
| UI | Company **Policies** page, project **Policies** section |

Why this does not collide:

- The machine-enforced policies already sit under their own domain:
  - `/companies/:id/tools/policies` (`tool_policies`);
  - `/companies/:id/skill-policy` (`company_skill_policies`);
  - `/companies/:id/budgets/policies` (`budget_policies`);
  - `/users/.../inbox-agent-policy`;
  - JSON fields such as `executionPolicy` and `runContextPolicy`.
- The bare `/companies/:id/policies` path, the `policy://` scheme and a top-level
  `policy` CLI command are free.
- The table carries the `company_` prefix like `company_skills` and
  `company_secrets`. The shared type is `CompanyPolicy`, never a bare `Policy`.
  `ToolPolicy`, `BudgetPolicy` and `IssueExecutionPolicy` stay distinct.
- Docs and UI copy describe a policy as written guidance and link to the
  enforced settings (tool policies, skill policy, budgets, approvals) where those
  are the right tool.

## Data model (slice 1)

`company_policies` reuses `documents`, the same way `routine_documents` and
`issue_documents` do:

- `id`, `company_id` (cascade);
- `project_id`: null for a company policy, set for a project policy (cascade);
- `document_id`: unique, cascade. The document holds the title, the body and
  the revision history (`document_revisions`), with author and timestamps;
- `key`: a slug, unique per company across both scopes, so `policy://<key>`
  always names one policy. The key is immutable;
- `summary`: optional, one line, at most 280 characters. Lists and prompt
  assembly (slice 2) show it instead of the full body;
- `status`: `draft`, `active` or `archived`, default `draft`. Archive is the
  normal way to retire a policy: the key stays reserved, so a `policy://<key>`
  reference never points at a different policy later. A board-only hard delete
  exists, and the UI offers it only for an archived policy. The slice 2 resolver
  reports an unknown or archived key, and never drops it silently;
- `owner_agent_id` / `owner_user_id`: optional, at most one of them set;
- `created_at`, `updated_at`.

Indexes: unique `(company_id, key)`, unique `(document_id)`, and
`(company_id, project_id, status)`.

Deleting a project deletes its policies, their documents and their revisions in
one transaction. The `project.deleted` activity entry lists the removed keys
(`removedPolicyKeys`).

### Invariants

Later work, including any enforcement work, keeps these:

1. The key is immutable and unique per company. Archive keeps it reserved.
2. Writes are board-only and agents only read. An enforceable control must never
   become agent-writable. One accepted exception: deleting a project deletes its
   policies, and an agent may delete a project of its company. That works only
   while the project has no issues, so no task is left that its policies govern.
   The `project.deleted` activity lists the removed keys. A later enforcement
   table must revisit this exception before it attaches controls to project
   policies.
3. `company_policies.id` is the stable identity. A hard delete cascades.
4. `company_policies` gets no free-form metadata or config `jsonb`, and no
   "enforced" status. `status` stays `draft`/`active`/`archived` and means
   guidance visibility only. If enforcement comes later, it goes in a separate
   child table (for example `company_policy_controls`: `policy_id` cascade,
   `company_id`, `kind`, a zod-validated `spec`, and `mode` `audit|enforce`), as an
   additive migration.

## Access (all slices)

- **Board:** full CRUD.
- **Company agents:** read only. Parity of surfaces is not parity of
  permissions: agent keys get list, get and history through REST, CLI and
  runtime tools, and every write returns 403.
- **Other companies:** 404/403 through the existing company access check.
- **Activity log:** `policy.created`, `policy.updated` (with the changed fields
  and the new revision number; archiving is an update), `policy.deleted`.

## Slices

### Slice 1: the resource and CRUD

- **db:** the table, the export and the generated migration.
- **shared:** types, zod validators (key slug, status, summary cap) and the
  status constants.
- **server:**
  - a `company-policies` service: list (filter by scope, project and status),
    get by key, create, update, delete and revision list;
  - routes under `/companies/:companyId/policies` with board-only writes;
  - the activity log entries;
  - OpenAPI entries, with the writes marked board-only.
- **UI:**
  - a company Policies page (sidebar Org section). It groups company and project
    policies and has a "Show archived" toggle. The REST list and the CLI filter
    by scope, project and status;
  - a Policies section on the project Configuration tab (no "New policy" on an
    archived project);
  - one editor dialog (title, key, summary, markdown body, status, project, and
    an owner that is a person or an agent);
  - a revision history view with view and restore.
- **CLI:** `paperclipai policy list|get|create|update|delete|history`.
- **Skill:** a new `references/policies.md`, a pointer in `SKILL.md`, and a
  block in `references/api-reference.md`. New sections go last in `SKILL.md` and
  `api-reference.md`, and each new heading gets a row in
  `packages/paperclip-runner/spec/capability/capabilities.yaml` (the capability
  inventory anchors headings by line).
- **Tests:**
  - route tests: CRUD, board-only writes, agent reads, a cross-company denial,
    the key conflict, the stale base revision, the activity rows, and project
    deletion;
  - CLI tests;
  - component tests: the editor's PATCH builder and the error reset;
  - a Playwright flow at 1440 and 390 px.

### Slice 2: references and prompt assembly

- `policy://<key>` in `packages/shared/src/project-mentions.ts`: the regex, the
  parser and the extractor.
- UI:
  - chips (`mention-chips.ts`, the `MarkdownBody` `urlTransform`, chip-to-route);
  - `/policy` autocomplete in the markdown editor.
- A resolver that scans these places for `policy://` mentions:
  - the issue text, as for `skill://`;
  - the agent's instructions, read from the stored revision and never from the
    per-run working copy;
  - routine and step text, which reaches the run as issue text;
  - company skill markdown.
- Prompt assembly sets `context.paperclipPolicies`, an index of the policies
  that apply. Each entry is the key, title, summary and scope:
  - the company's active policies;
  - the active policies of the task's project;
  - any active policy that is mentioned.

  It renders in `selectPaperclipPromptSections` as a board-authored
  "## Policies" section. Every adapter and native run gets it.
- Token budget:
  - the prompt carries only the index, never a full body;
  - the index is capped (entries and characters), with a "+N more" line;
  - the full text is fetched on demand with `GET .../policies/:key` or
    `paperclipai policy get <key>`;
  - the index is sent on a fresh session. On a resumed session it is sent again
    only when its content hash changed. The last-sent hash lives in the task
    session's params, with no new table. If that has no clean home, a resumed
    session gets only a one-line "policy index changed" note.
- Resolver cost:
  - scans of stored instructions and skill markdown are cached by revision id
    or content hash;
  - a test shows that a run with no mentions adds at most one bounded query.
- Two constraints on prompt assembly:
  - the index is never written into the instructions working copy, which is
    collected back as agent edits;
  - it stays out of the Claude prompt-bundle hash, so resumes keep working.
- `GET /api/issues/:id/heartbeat-context` gains a `policies` index.
- A `policy://` mention brings in guidance only. Issue text can come from a
  low-trust or external source, so a mention must never attach anything that
  limits or blocks a run. Any later enforcement attaches only from board-authored
  scopes: company, project, routine or agent configuration.
- Tests:
  - the prompt size with 0, 5 and 50 policies, measured before and after;
  - the cap holds;
  - a resumed session does not repeat an unchanged index;
  - mention resolution from each source.
- Focused independent review of the `heartbeat.ts` and adapter changes.

## Guidance and enforcement

| Rule | Where it lives |
|---|---|
| Working norms: code style, review expectations, tone, escalation habits, "open a PR for every change", documentation rules | **Policy** (prompt-level guidance) |
| Who may hire, and which actions need board approval | Server: approvals, `requireBoardApprovalForNewAgents` |
| Review and approval stages before a task is done | Server: `executionPolicy` / `reviewPolicy` stages |
| Spend limits | Server: budget hard-stop (`budgets.ts`) |
| GitHub writes, write identity, protected branches | Server: GitHub operation classifier and access checks |
| Which tools an agent may call; tools that need approval or are rate limited | Server: `tool_policies` engine |
| Which skills an agent may use | Server: company skill policy |
| Protected agent config changes | Server: `agent-protected-change-guard.ts` |
| What a remote sandbox run may call back | Server: callback bridge allowlist |
| Low-trust content containment, cross-issue influence limit | Server: as today |

A policy can say "this is enforced by …" in its body and link to the setting. If
a rule must hold even when the agent ignores it, it belongs to one of the server
mechanisms above, not to a policy. A structured pointer from a policy to an
enforcing rule is a later option. It is not in these slices.

## Out of scope

- A rules engine.
- Policy approval workflows.
- Agents editing policies.
- Per-agent or per-routine policy scopes.
- Policies in company export and import.
